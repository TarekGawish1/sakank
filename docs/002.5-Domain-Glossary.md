# 002.5 — Domain Glossary (Ubiquitous Language)

## 1. Executive Summary

The foundation of Domain-Driven Design (DDD) is the **Ubiquitous Language**—a shared, rigorous vocabulary used identically by product managers, engineers, designers, and business stakeholders. When engineering uses different terminology than operations, bugs occur, systems break, and the database becomes a spaghetti of overlapping concepts. This document establishes the single source of truth for the Sakank domain. No subsequent document (API design, database schema, or UI mockup) is permitted to invent new terms or alter these definitions.

## 2. Naming Principles

To maintain linguistic purity across the architecture, all teams must adhere to the following rules:

1. **Use Singular Nouns:** A domain concept is singular (e.g., `Property`, not `Properties`) unless explicitly describing a collection.
2. **Avoid Synonyms:** Choose one word and stick to it. If we use `Owner`, we never use `Landlord` or `Host`.
3. **Business Language First:** Terms must reflect how the business operates in the real world, not how the database stores it (e.g., `Stay Request`, not `User_Property_Mapping`).
4. **No Tech Jargon in Domain:** Avoid words like `Manager`, `Handler`, or `Processor` in domain nouns unless they represent a physical human role (e.g., `Property Manager`).
5. **Stable Names:** Core concepts should not change. If a business pivot occurs, we explicitly deprecate the old term and introduce a new one.

## 4. Entity Candidates

In Domain-Driven Design, these terms map to specific architectural patterns:

| Term               | DDD Type       | Rationale                                                                                                                        |
| :----------------- | :------------- | :------------------------------------------------------------------------------------------------------------------------------- |
| **Student**        | Aggregate Root | Has a global identity; independently manages its lifecycle and profile data.                                                     |
| **Owner**          | Aggregate Root | Has a global identity; owns properties and manages requests.                                                                     |
| **Property**       | Aggregate Root | Controls the physical location and acts as the parent for `Unit`s.                                                               |
| **Unit**           | Entity         | Has identity within a `Property`; lifecycle is bound to the Property but has its own pricing/availability.                       |
| **Stay Request**   | Aggregate Root | Highly transactional. Has its own complex state machine (Pending -> Accepted). Must enforce invariants between Student and Unit. |
| **Address**        | Value Object   | No identity. Two properties with the exact same address details share the same value. Immutable.                                 |
| **Verification**   | Domain Service | The logic to verify an Owner or Property involves multiple aggregates and external services.                                     |
| **Listing Status** | Enumeration    | A strictly defined, bounded set of states governing visibility.                                                                  |

## 5. Enumerations

Official states that must be identical in the Database, API, and Mobile App.

**Listing Status**

- `Draft`: Incomplete, only visible to Owner.
- `Pending Verification`: Submitted, awaiting Admin review.
- `Approved`: Live and visible in public search.
- `Rejected`: Denied by Admin (requires a reason).
- `Hidden`: Temporarily paused by Owner (not visible, but approved).
- `Archived`: Permanently removed by Owner.

**Availability (For a Unit/Bed)**

- `Available`: Can receive new Stay Requests.
- `Reserved`: Owner verbally agreed, pending final move-in (blocks new requests).
- `Occupied`: Rented out.
- `Unavailable`: Offline for maintenance or other reasons.

**Stay Request Status**

- `Pending`: Submitted by Student, awaiting Owner action.
- `Accepted`: Owner agreed; contact info is shared.
- `Rejected`: Owner declined.
- `Cancelled`: Student withdrew before Owner action.
- `Expired`: Owner did not respond within the SLA (e.g., 48 hours).

## 6. Forbidden Terms

To maintain domain purity, the following terms are banned from the codebase, UI, and documentation.

| Banned Term      | Replace With             | Why?                                                           |
| :--------------- | :----------------------- | :------------------------------------------------------------- |
| Booking          | **Stay Request**         | MVP does not process financial transactions.                   |
| Reservation      | **Stay Request**         | Implies a guaranteed hold. A request is just a lead.           |
| Hotel            | **Property / Dormitory** | We do not do nightly/hospitality stays.                        |
| Guest / Traveler | **Student**              | "Guest" implies short-term tourism.                            |
| Host / Landlord  | **Owner**                | "Host" is Airbnb terminology. "Landlord" is too archaic/legal. |
| Vacation         | **Academic Term**        | Entirely wrong user intent.                                    |
| User             | **Student / Owner**      | Too generic. Code must explicitly declare the actor.           |

## 8. API Naming Conventions

APIs must use `camelCase` and avoid arbitrary abbreviations. Use full domain terms.

- **Correct:** `stayRequest`, `propertyOwner`, `verifiedProperty`, `listingStatus`
- **Incorrect:** `req`, `propOwn`, `verProp`, `status`

_Examples:_

- `GET /api/v1/stayRequests/{id}`
- `POST /api/v1/properties/{id}/units`
- `PATCH /api/v1/listings/{id}/status`

## 9. Database Naming Conventions

Database tables must use `snake_case`, pluralized nouns matching the domain glossary exactly. Do not use prefixes like `tbl_`.

- `students`
- `owners`
- `properties`
- `units`
- `stay_requests`
- `favorites`
- `reviews`
- `notifications`
- `universities`
- `regions`
- `amenities`

## 10. Future Reserved Terms

These concepts are intentionally excluded from MVP to prevent scope creep, but their names are reserved for future architectural phases.

- **Payment:** Handling digital transfers (requires gateways, PCI compliance).
- **Escrow:** Holding a deposit until move-in (requires complex financial legalities).
- **Lease / Contract:** Legally binding digital agreements (requires e-signature integrations).
- **Roommate:** Student-to-student matching (requires complex compatibility algorithms).
- **Subscription:** Recurring payments for premium features.
- **Maintenance:** Ticketing system for broken facilities.
- **University Partnership:** B2B portal for universities to bulk-book rooms.

## 11. Final Recommendation (Enterprise Architect Directive)

**The "Ctrl+F" Rule:**
Before any PR (Pull Request) is merged, any API spec is finalized, or any Figma screen is approved, the reviewer must mentally (or literally) run "Ctrl+F" against this glossary.

- If a frontend developer names a variable `bookingStatus`, the PR must be rejected.
- If a PM writes a user story saying "The Guest wants to message the Host", it must be rewritten.
  Enforcing this strict Ubiquitous Language from Day 1 is the single highest-leverage technical decision a startup can make to prevent technical debt.
